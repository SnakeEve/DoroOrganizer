# Decisions log

Baseline for every design doc and all code. It resolves gaps and contradictions in the [spec](../stakeholder-notepad-spec.md), cited as §n.

- **Precedence:** this file > spec > other files in `docs/`. If a doc or code disagrees with this file, this file wins. Change a decision here first, then update the docs.
- **Status:** `Decided` means an engineering decision. `Owner` means the default stays in force until the product owner answers the linked question.
- Cite decisions as `DEC-nn` in docs, code comments and PRs. Never renumber. Mark a replaced entry "Superseded by DEC-nn".

## Security

| ID | Decision | Why / spec | Status |
|---|---|---|---|
| DEC-60 | Key model with three modes. **Plain:** key `ByteArray(0)`. **Device:** a random 32-byte DEK, wrapped by a non-exportable AndroidKeyStore AES-256-GCM KEK (`setKeySize(256)`, no user-auth flags, no `setUnlockedDeviceRequired`, StrongBox when available with fallback). **Password:** the DEK is first wrapped by AES-GCM under PBKDF2-HMAC-SHA256(password, 16-byte salt, ≥ 600,000 iterations, calibrated to about 0.5–1 s), then by the Keystore KEK. SQLCipher gets the DEK in raw-key form (`x'<64 hex>'`, no per-connection KDF). The mode, wrapped DEK, IVs and KDF parameters live in the key-state file (DEC-80). All modes are off at first run. **Biometric slot** (Password mode with the biometric lock on, Q8): the DEK is also wrapped by a second AndroidKeyStore AES-256-GCM key that needs a `BIOMETRIC_STRONG` authentication for every use (`setUserAuthenticationRequired(true)`; API 30+ `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)`, API 28–29 validity −1) with `setInvalidatedByBiometricEnrollment(true)`. It is unwrapped through a BiometricPrompt `CryptoObject` and stored as a second slot in the key-state file. The biometric key is TEE-backed (no StrongBox). The slot wraps the DEK on its own, outside the KEK layer. The key-state keeps format version 1 with the biometric slot as an optional member; a damaged or dead biometric slot is ignored (password route) and never makes the key-state invalid | §8, §11 (errata); Q1, Q8 answered | Decided |
| DEC-61 | Every key change (enable, disable, set, change or remove the password) creates a new DEK and runs the export-and-swap pipeline (DEC-82), so the database is literally re-encrypted. It requires the current password when one is set, except the fingerprint password reset of DEC-63 | §11 "re-encrypts the database" | Decided |
| DEC-62 | Password mode asks for the password at cold start, before the database opens, whenever the fingerprint unlock of DEC-65 is not available. On return from background it is asked when the biometric lock is on and the fingerprint route is not available (DEC-65), when the 14-day reminder is due (DEC-74), or when the user chooses "Use password"; with the lock off, nothing is asked. A wrong password fails the GCM tag on the inner wrap and is never treated as corruption. Attempts are unlimited; after 5 consecutive failures a delay applies, starting at 30 s and doubling up to 5 min. The delay runs on the monotonic clock (`AppTime.elapsedMillis()`), so clock changes have no effect, and the full delay is re-applied after a reboot. `KeyVault` alone owns the failure counter and retry time and persists them before it answers. Empty or malformed input is answered as a wrong password without running PBKDF2 and without counting | §11, §13.8 | Decided |
| DEC-63 | Forgotten password: "Forgot password?" explains the options. When fingerprint unlock is available (DEC-65) it first offers "Set a new password with your fingerprint": the fingerprint unwraps the DEK through the biometric slot, and a key change (DEC-61) sets the new password without the old one. Otherwise, or if the user prefers, it offers "Erase all data and start over" behind a typed confirmation, which deletes the database files and the key state, resets the security settings and lands in the first-run state, where Restore is available. The fingerprint reset is offered whenever a usable biometric slot exists, whatever route led to the password screen, on the cold-start password screen and on the password screen of a lock (database open), never from Corrupt; if the slot's key does not match the live key, nothing changes and an error is shown. The broken-key notice (KEK failure detected behind a working slot) offers "Back up now" and points to "Forgot password?"; it does not start the reset itself. Any finger enrolled when the slot was created can reset the password (enrolling a new finger invalidates the slot first). Erase is offered on every startup-password screen; with the database open it first closes Room in exclusive mode and ends with a restart (while an operation runs behind a locked password screen, "Forgot password?" and with it Erase are hidden). A fingerprint reset counts as the unlock: while it runs the gate shows progress and never prompts for the fingerprint; on success the gate goes to Ready and the slot re-creation offer follows; if it rolls back (Aborted) it returns to the password screen it started from. Outcomes that leave no open database (failed reopen, corruption found, unknown commit outcome) end in a fresh lock, Corrupt or a restart instead. A reset started from the cold-start password screen hands its committed key to `Opening` (`OpenWithNewKey`, `DbMaintenance.takeResetKey`), so the live Room instance is still built only in `Opening` (DEC-90). If the app is sent to the background during a reset, the lock is recorded and a successful reset ends in Locked(Ready) instead of Ready | §8; Q8 follow-up | Decided |
| DEC-64 | Passwords: entered twice when set, at least 8 characters, no composition rules, plus an "I understand this cannot be recovered" checkbox. Handled as `CharArray` → NFC → UTF-8 `ByteArray`, zeroed after use. Never stored in `SavedStateHandle`, Bundles or navigation keys. `KeyVault` zeroes the 32-byte DEK as soon as it has built the 67-byte raw-key encoding; `DatabaseHolder` keeps that raw key only while the database is open and zeroes it after `close()`. Arming the biometric slot decodes the DEK from a copy of the live raw key and zeroes both after wrapping | §11 | Decided |
| DEC-65 | Biometric lock (androidx.biometric 1.1.0, `BIOMETRIC_STRONG`). The toggle is shown only when `canAuthenticate` = SUCCESS (STATUS_UNKNOWN: allowed after a successful test prompt; NONE_ENROLLED: disabled, with an enroll hint). Turning it on or off requires one successful authentication; in Password mode, turning it on creates the biometric slot (DEC-60) and turning it off deletes the slot and its Keystore key. In Password mode, creating the slot anywhere except the re-creation offer that directly follows a successful password entry (turning the lock on, set-up from Settings) first asks for the startup password, then the fingerprint, so a finger enrolled by someone who only knows the device PIN can never arm it. In Password mode the lock is turned off with the fingerprint through the slot or with the startup password (always the password when the slot cannot authorize), never with the device credential. Toggles write the setting first, then arm or remove the slot; removal deletes the Keystore key before rewriting the file; the gate never uses a slot while the lock is off, and the lock reconciliation (`AppLockController.reconcileLock()` after the next password unlock; the startup reconciliation never touches a slot) removes leftovers. Locks at cold start and when the process returns from background (`ProcessLifecycleOwner` ON_STOP → ON_START), with no grace period, except a one-shot exemption (at most 10 min) for external activities the app launched itself (SAF, share sheet, enrollment, the API 28–29 device-credential confirmation). **Unlock method, fingerprint first (Q8):** with the lock on and a usable strong biometric, the fingerprint alone unlocks, at cold start and on return from background, in every mode; in Password mode it unwraps the DEK through the biometric slot, and the prompt's negative button is "Use password". Without a usable strong biometric (none enrolled, hardware unavailable, permanent lockout, slot invalidated): Password mode asks the startup password alone; Plain and Device modes fall back to the device screen-lock credential (Q7; API 30+: `DEVICE_CREDENTIAL` prompt; API 28–29: `KeyguardManager.createConfirmDeviceCredentialIntent`). A fingerprint enrollment change invalidates the slot: the password unlocks, then one fingerprint prompt re-creates the slot (if cancelled, it is offered again after the next password unlock). Every key change (DEC-61) makes a new DEK, so a key change that ends in Password mode with the lock on finishes with the same re-creation prompt. Without a secure lock screen the lock turns off with a notice; in Password mode only after the startup password has been entered, so removing the screen lock never bypasses the password. Over KeyUnavailable no key-state can check a password, so the lock uses the fingerprint with the device-credential fallback in every mode (DEC-86). A rarely typed password is kept fresh by the 14-day reminder (DEC-74), and a forgotten one can be replaced with the fingerprint (DEC-63); backups remain the last safety net (DEC-73). `ExternalActivities` owns every activity-result launcher, the credential confirmation included; `AppLockController` drives `BiometricPrompt` through the platform adapter `BiometricGateway` | §8, §11 (errata); Q7, Q8 answered | Decided |
| DEC-66 | While locked, the content UI is not composed and the gate screens show no note-derived data. On API 33+, `setRecentsScreenshotEnabled(false)` while the biometric lock or encryption is on. While the settings or the key mode are unknown the window policy is closed: FLAG_SECURE on, Recents screenshot off, overlay windows hidden (this includes KeyUnavailable with an invalid key-state). On API 31+ overlay windows are hidden (`setHideOverlayWindows`) in every gate state except `Ready` and `Maintenance` from `Ready` (overlays stay allowed on the progress screen of an Erase started from `Ready`: it shows no data and has no controls). System content capture is off on API 29+. Over a locked password screen only the fixed-text failure dialogs of a fingerprint reset or an Erase may appear (ui.md § 8.12, lock mode) | §11 App Lock | Decided |
| DEC-67 | Screenshot protection = `FLAG_SECURE` on the whole activity window, set before the first frame and live on toggle. Compose dialogs, popups and sheets keep `SecureFlagPolicy.Inherit` (never `SecureOff`) | §11 (errata) | Decided |

## Database lifecycle

| ID | Decision | Why / spec | Status |
|---|---|---|---|
| DEC-80 | Live database = `databases/doro-<generation>.db`. Key-state file = `noBackupFilesDir/db-state.json`, written with `AtomicFile`. It holds the format version, the current generation and the key slot (mode, wrapped DEK, IVs, KDF parameters), plus the optional biometric slot (DEC-60). Committing a swap = atomically rewriting this file. Creating or removing the biometric slot is a slot-only commit: the same atomic rewrite with the same generation and no database swap; a slot-only commit whose read-back fails is repaired by rewriting the main slot read under the same mutex, without the biometric slot; this repair is allowed only for a file the same operation read as valid and has just written itself (it is not an automatic rewrite of an invalid file, DEC-86). Removing the slot deletes the Keystore key first and skips the file rewrite while another operation holds the operation mutex (a dead slot is tolerated, DEC-60). Startup deletes unreferenced `doro-*` files and leftover staging/share temp files | §11 atomic replace | Decided |
| DEC-81 | `DatabaseHolder` alone owns the Room instance. Nothing caches a DAO or the database. Observers go through the holder (`flatMapLatest` on its state), so flows survive a swap. Exclusive maintenance mode drains in-flight work, closes Room, runs the operation and reopens | | Decided |
| DEC-82 | One export pipeline (`DbMaintenance`) serves backup, restore and key changes. It uses a dedicated SQLCipher maintenance connection (never ATTACH through Room), `ATTACH DATABASE ? AS target KEY ?` with the key always bound explicitly (a null key silently reuses the source key), and `SELECT sqlcipher_export('target')` through a query (never `rawExecSQL`, which swallows errors). It then sets the target's `user_version` and `application_id` (not copied by export) and verifies the target: reopen, `integrity_check`, `foreign_key_check`, `cipher_integrity_check` when encrypted | §11 | Decided |
| DEC-83 | A backup is always an export, never a byte copy of the live file. It is plaintext only if the database is Plain and "Encrypt backups" is off. Otherwise it is a SQLCipher 4 passphrase-mode file keyed with a backup password entered twice at export time (required whenever the database is encrypted). Default name `doro-organizer-backup-YYYY-MM-DD.db` (local date). Primary path: SAF `CreateDocument("application/octet-stream")`, written with mode `"wt"`. Secondary path: share sheet via a FileProvider over `cacheDir/share/`, whose files are deleted at the next export, at cold start, after one hour and after every committed key change. A plaintext export is preceded by a warning. A database that fails `quick_check` is not backed up | §10, §11 (errata) | Decided |
| DEC-84 | Restore: SAF `OpenDocument("*/*")` → staged copy in `noBackupFilesDir` → header sniff ("SQLite format 3\0" = plain, else ask for the backup password) → validation (`application_id`, `user_version` ≤ current, Room identity hash when equal, `integrity_check`, `foreign_key_check`, expected tables, and data-layer.md's restore checks R-1..R-5: DEC-22 invariant, content size, date range, column value types, name length) → migrations on the staged copy → export into the device's current key configuration → confirmation dialog (backup note/person/project counts, irreversible replacement, the resulting encryption state) → swap → navigation resets to All and remembered selections and filters are cleared. Restore never changes security settings, with one exception: a restore started from KeyUnavailable writes a Plain key state and deletes the KEK (DEC-86), and its confirmation says so. From the Corrupt screen in Password mode the key for the export is obtained fingerprint first through the biometric slot (a due reminder, or a failed or cancelled prompt, asks for the password). Restore from Ready or Corrupt keeps the key slots, the biometric slot included (same DEK); in a restore from Corrupt, a slot-released key that fails the slot-key check deletes the biometric key, so the kept slot is dead and the next unlock uses the password (DEC-60) | §8, §11 | Decided |
| DEC-85 | Nothing deletes the database without an explicit user action. Corruption = open or `quick_check` failure with a key known to be correct, or `SQLiteDatabaseCorruptException` at runtime. It shows the Corrupt screen (after authentication) with "Restore from backup" and "Start fresh" (confirmation; deletes the database files and creates an empty Plain database, with a notice that encryption is now off). The file is kept until the user chooses | §5 (errata), §13.6 | Decided |
| DEC-86 | The KeyUnavailable screen appears when the key cannot be obtained: a Keystore error; an invalid key-state file, whatever database files exist (plaintext-only or none, because a plaintext file may be a superseded generation and an invalid key-state is never rewritten automatically); or a missing key-state file next to a main database file that is not recognizably plaintext. It offers Restore from backup and Start fresh; both produce a Plain database and delete the KEK and the biometric key. Never delete automatically. A Keystore failure while checking a password over an open database is a failed check, not KeyUnavailable; a damaged biometric slot never causes KeyUnavailable (DEC-60). In Password mode with a live biometric slot (Password mode, lock on, slot status Live; a stale slot left with the lock off does not count), a KEK failure during a password unlock is not KeyUnavailable either: the gate falls back to the fingerprint route, even when the reminder is due (the reminder is ignored for the rest of the process), and shows the broken-key notice. The same fallback applies to the key of a restore from Corrupt: a KEK failure on its password path with a live slot asks for the fingerprint instead of ending in KeyUnavailable. With a live slot but no usable strong biometric at that moment, the password screen explains that the device key store failed and that the fingerprint or a backup restore is the way back | §11 | Decided |
| DEC-87 | Crash safety: every operation writes staging files in `noBackupFilesDir`, and the only commit point of a swap is the key-state rewrite. A crash before the commit leaves the old database live; startup cleanup removes leftovers | §11 atomic replace | Decided |
| DEC-88 | Never `fallbackToDestructiveMigration*`, never `allowDataLossOnRecovery`. Every change to a released schema version ships a migration and a migration test (DEC-14) | §1 (recovery only via backup) | Decided |
| DEC-89 | Journal mode: Room default (WAL). Maintenance runs with Room closed, so the WAL is checkpointed and removed. `-wal` and `-shm` files are never copied | §11 Backup / Restore | Decided |
| DEC-91 | Downgrade: a live database whose `user_version` exceeds `AppDatabase.VERSION` (an older app installed over newer data) is classified Transient and shows the generic open-error screen with Try again. Nothing is deleted or migrated; there is no dedicated state in v1 | Reachable only through sideloaded downgrades | Decided |

## Session gate

| ID | Decision | Status |
|---|---|---|
| DEC-90 | `SessionGate` (application scope) owns the startup and lock state machine. States: `Starting` → `NeedsPassword` (Password mode without a usable biometric slot, or with the reminder due) or `Locked` (biometric lock on: Plain and Device modes, and Password mode with a usable biometric slot) → `Opening` (unwrap the key, open, verify) → `Ready` \| `Corrupt` \| `KeyUnavailable`. `Ready` → `Locked` on return from background when the lock is on (in Password mode the lock shows the password entry over the open database whenever DEC-62 requires the password); `Ready` ⇄ `Maintenance` during DEC-82 operations. The live Room instance is built only in `Opening`, never in `Application.onCreate`; `DbMaintenance` may build temporary Room instances on staged copies under `noBackupFilesDir`. `NavDisplay` is composed only in `Ready` and in `Maintenance` that started from `Ready` (behind a blocking progress overlay; an Erase shows the progress screen whatever its origin); `Maintenance` from any other origin shows a progress screen. Activity-result launchers are registered at activity level so a lock never drops a pending result. Gate screens own no ViewModel, except the activity-scoped `ForgotPasswordViewModel` (no repository, no data, no password property; its state is only the busy flag, the local error and the fingerprint-availability answer), so the fingerprint reset survives rotation | Decided |
