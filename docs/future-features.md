# Future features

Ideas for later builds of Doro Organizer (now 2.6.0, DEC-115). Nothing here is a commitment. An item is built only after the owner says go, a design run, new rows in [SPEC.md](../SPEC.md) §T (and §V where a rule changes), and a version counted by DEC-115.

## How to use this list

- **Owner:** read "What it gives you" and "Size". To start one, tell a session its ID (for example "design FF-10"); the session then runs a design and asks before anything is built.
- **Size:** S = one small task. M = a task with its own UI, a DEC and phone tests. L = several tasks, often a new screen, a file format or a schema change.
- **Notes** give the owner's decision and its date, the [CLAUDE.md](../CLAUDE.md) "Rules that must never break" an item touches ("rule 7" is rule no. 7 there), and what it needs first. "VERSION 2" means a schema change: `AppDatabase.VERSION` 2 with a migration, its test and a committed schema JSON (rule 11). The app has never had a schema version 2: version 1 is released and frozen (it was last changed in place, before the release, by DEC-106).
- **Sources** under each table point to the records. R- and S- ids come from [REQUEST_AND_SUGGESTION.md](../REQUEST_AND_SUGGESTION.md); paths under `build/` are local session records, not in git. Line numbers are as of 2026-11-26.
- **Precedence:** [decisions.md](decisions.md) wins over this list. When an item is decided, built or dropped, change its row here in the same commit (built: remove it and name its SPEC row; dropped: move it to section 4).
- **Privacy:** this file names no note text, people or projects; owner notes are cited by number only.

Every item must keep these rules: offline only (no network, no INTERNET permission, no analytics or crash reporting); no user data in logs; SQLCipher only; every list in the single canonical order (DEC-23), so an idea that needs another sort order conflicts and says so; hard deletes only (no history, undo or deduplication); no destructive migration; all text from strings.xml.

## How to pick the next build

Weigh what an item gives you in daily use against its size: S items with a clear daily gain (FF-10 Lock now, FF-01 status filter, S-11, FF-12) fit beside a fix such as R-4b-F-b1 in one build, while an L item (R-5 with S-7, FF-07) is a build of its own. Before choosing, run the rule checks on it: offline only, no user data in logs, SQLCipher only, the single canonical order, hard deletes only, and whether it needs VERSION 2. An item that needs a schema change waits for T23's M-20 fixtures and the L-10 restore test, and any new tables are planned into one v2 migration. An item that needs another note order, deduplication, history or a network cannot be built until the owner changes that rule, wherever it is listed (S-1d and S-6 in section 1 included); one that needs another picker order needs a DEC over DEC-32. Then the owner says go, a design run writes the DEC and SPEC rows, and the version follows DEC-115.
