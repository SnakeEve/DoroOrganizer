# Testing

This document defines how Doro Organizer is verified: test layers, devices, the order in which suites must exist, the invariant catalog, security and lifecycle tests, §13 traceability, fixtures and fakes, performance measurement, CI gates and the manual release checklist.

Related: [decisions.md](decisions.md) · [architecture.md](architecture.md) · [data-layer.md](data-layer.md) · [ui.md](ui.md) · [security.md](security.md) · [db-lifecycle.md](db-lifecycle.md) · [spec](../stakeholder-notepad-spec.md)

Conventions: catalog ids are `I-nn` (invariants and behavior), `L-nn` (security and lifecycle), `P-n` (performance) and `M-nn` (manual). Catalog ids always carry two digits (`I-05`). data-layer.md numbers its invariants `INV-1` to `INV-12` and its restore checks `R-1` to `R-5` ([data-layer.md](data-layer.md) § Invariants), so a bare `I-nn` here is always a catalog id. Other docs cite catalog ids with the prefix "testing.md". "Instr" means instrumented. The mapping from data-layer.md's invariants to catalog rows is at the end of [section 4](#4-invariant-catalog).

Rules for every test:
- Anything that touches SQLCipher is instrumented (DEC-12): its `.so` files cannot load on the JVM or under Robolectric. No DAO, query or migration test may run on the framework SQLite instead, because its `LIKE` is ICU-enabled and its error handler deletes files (DEC-08). Robolectric is not used.
- No mocking library (DEC-12). Fakes are hand-written. Code that never calls Android at runtime (`FakeAppTime`, `FakeKeyVault`, `FakeSettingsStore`, `SENTINEL`, the pure `SeedModel` generator, the oracle comparator, `ThrowingFaultHook`) lives in `app/src/sharedTest/java/com/doro/organizer/testing/`, a directory that `app/build.gradle.kts` adds to the `test` and `androidTest` source sets ([section 9](#9-ci-pipeline) sketch). Everything that needs a `Context`, SQLCipher or androidx.test (`DoroTestRunner`, `TestDoroApplication`, `DoroAppRule`, `TestDatabases`, `FakeBiometricGateway`, the seed database writer, `corruptPage`, `fileFingerprint`, `canonicalDump`, the annotations `PerfTest`, `PageSizeSmoke`, `ReleaseSmoke` and `RealBiometric`) lives in `app/src/androidTest/java/com/doro/organizer/testing/`, so a JVM test can never compile against SQLCipher helpers. Verify at setup: AGP's `testFixtures` is not used because it targets library modules; if AGP 9.5 supports it for an application module it may replace `src/sharedTest`.
- No fake exists for `NoteRepository`, `EntityRepository`, `DatabaseHolder` or `DbMaintenance`, so no fake can drift from the SQL or the file protocol. The fakes are `FakeAppTime`, `FakeSettingsStore`, `FakeKeyVault`, `FakeBiometricGateway` and the hand-written process `LifecycleOwner` ([section 7](#7-fixtures-and-fakes)).
- JVM tests call no Android API at runtime (the stubs in `android.jar` throw). A class that needs a `Context`, a `Uri` or `android.icu` is tested instrumented. ViewModels are tested instrumented on the real repositories. JVM tests construct only the `SessionGate` reducer and pure policies directly.
- Instrumented tests are hermetic. Android Test Orchestrator with `clearPackageData=true` runs `pm clear` on the app after each test, which deletes its files, DataStore and Keystore entries; GMD runs start from a fresh install. Before the suite on a physical device, the runner script executes `adb shell pm clear <applicationId>`. No test depends on the order or leftovers of another.
- Behavior under test reads time only from `FakeAppTime` ([section 7](#7-fixtures-and-fakes)). To wait, use Turbine (`flow.test(timeout = 10.seconds) { }`; Turbine timeouts run on the wall clock) or `composeTestRule.waitUntil(timeoutMillis = 10_000) { }`. Give every `runTest` an explicit `timeout` (`runTest(timeout = 120.seconds)` when the 10,000-note seed is used). Never wrap work that runs on Room executors or `dispatchers.io` in `withTimeout` or `delay` inside `runTest`: virtual time would jump to the timeout at once. No `Thread.sleep`. `@PerfTest` measurements read `SystemClock.elapsedRealtimeNanos()` ([section 8](#8-performance-tests)). Dispatchers are injected as [architecture.md § Threading](architecture.md#threading) defines.
- Spec strings and ui.md strings are asserted as literals copied from the spec or from [ui.md § 11 Strings](ui.md#11-strings), never through `R.string`, so an edited resource fails a test (DEC-55). Nodes are found by the tags of [ui.md § 12.8](ui.md#128-test-tags).
- No owner question is open ([decisions.md § Owner questions](decisions.md#owner-questions)), so no test name carries a `_Qn` suffix. When a new question is opened, every test that pins its default ends its method name with the question id (`…_Q13`); only pinning methods carry the suffix, never a wildcard over a class, and answering the question starts with a search for `_Qn`. Answered questions are cited in the catalog text like decisions (for example "(Q7)"), never in test names.
- Tests never hard-code the applicationId `com.doro.organizer` (DEC-03): instrumented tests use `targetContext.packageName`, CI uses the value printed by `apkanalyzer manifest application-id` ([section 9](#9-ci-pipeline)).
- Every bug fix lands with a test that fails without the fix.
- Test library versions are pinned in `gradle/libs.versions.toml` with the rest of the stack ([architecture.md § Stack and versions](architecture.md#stack-and-versions)). Verify at setup: current stable Turbine, AndroidX Test (runner, rules, ext-junit, orchestrator, espresso-intents, uiautomator) and Compose UI test through the BOM.

### 2.1 Biometric slot tests: what runs where

The Q8 unlock (DEC-60, DEC-65) cannot be tested end to end with a fake. A `BiometricPrompt` that carries a `CryptoObject` only authorizes the cipher after a real touch on a real sensor, the biometric key ([security.md § 3](security.md#3-key-model-dec-60), which owns its parameters) can only be generated while a strong biometric is enrolled, and its invalidation is triggered by a real enrollment change in system Settings. The suites are therefore split:

| What | Tests | Runs on | Why there |
|---|---|---|---|
| The production `KeyGenParameterSpec` of the biometric key, inspected without generating a key | `BiometricKeySpecTest` (L-30) | GMD `api28` and `api35`, every PR | Building a spec needs no enrolled biometric |
| Slot creation, unwrap, deletion and re-creation logic, the gate paths, "Use password", the reminder, the fingerprint reset, the Q7 limit, the strings and screens | L-30–L-39, I-50, all except the device classes below | GMD `api28` and `api35`, every PR | Runs the real `KeyVault` with the test configuration of the Keystore-operations seam and `FakeBiometricGateway` ([section 5](#5-security-and-lifecycle-tests), technique "Biometric slot") |
| Generating the auth-bound key, its `KeyInfo`, a real `CryptoObject` unlock, `doFinal` refused outside an authenticated prompt | `BiometricSlotDeviceTest` (L-30, L-31), annotated `@RealBiometric` | Physical A every release, Physical B once per release; an operator touches the sensor | Needs an enrolled Class 3 biometric and a human finger |
| Invalidation by a real enrollment change, a newly enrolled finger refused, real re-creation, the reminder and the reset on the owner's phone | M-22–M-25 | Physical A (the owner's Poco F7) | Enrollment is a system-Settings flow that a test cannot drive |
| API 28–29 key parameters with a real touch (validity −1) | M-02 | Physical B | The only API 28–29 hardware in the matrix |

- `@RealBiometric` tests run with `./gradlew :app:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.annotation=com.doro.organizer.testing.RealBiometric` on an unlocked phone with a PIN and exactly one enrolled fingerprint. Each test shows the prompt and waits up to 60 s on the wall clock (`composeTestRule.waitUntil(timeoutMillis = 60_000)`) for the operator's touch; a timeout fails the test. The class starts with `assumeTrue(canAuthenticate(BIOMETRIC_STRONG) == BIOMETRIC_SUCCESS)` so it is skipped, not failed, on a device without an enrolled strong biometric. The `device-tests` job excludes the annotation ([section 9](#9-ci-pipeline)).
- The Orchestrator's `pm clear` after each test deletes the app's Keystore entries, the biometric key included, so every `@RealBiometric` test creates its own slot.
- Verify at setup: whether an emulator image with a fingerprint enrolled through the Settings UI and `adb -e emu finger touch <id>` can generate and use an auth-bound key with `AUTH_BIOMETRIC_STRONG`. If it can, `BiometricSlotDeviceTest` may also run on a non-GMD emulator in a nightly job; it still does not replace Physical A, whose TEE and HyperOS behavior are what ships.

## 3. Priorities

Each suite exists before, or in the same PR as, the code it protects. A PR that changes an area without its suite does not merge. Rows that span several areas are split into halves: the holder and vault half comes with item 5, the gate half with item 7, the screen half with item 8.

1. Infrastructure, before the first entity: `TestDatabases`, `FakeAppTime`, `assertDbInvariants`, `ArchitectureTest` (I-41), `MigrationCoverageTest` and `SchemaJsonTest` (I-48), `DoroAppRule`.
2. DAO, canonical order, perspective query, filters and search: I-01–I-04, I-10–I-16, I-24–I-27, I-43, I-47.
3. Write rules and time, with the first `NoteRepository` write and `AppTime`: I-05–I-09, I-28–I-30, I-42 (a)–(c).
4. Links, with `EntityRepository` and the batch code: I-17–I-20, I-21 (repository part), I-23 (repository part), I-42 (d).
5. `DatabaseHolder` open, verify and failure classification plus `KeyVault`, before `SessionGate` opens anything and before an encrypted mode is reachable. Holder-level and vault-level assertions only: L-04, L-13, L-17, L-27, L-28, the `KeyVaultTest` and `DatabaseHolderTest` parts of L-03, and the classification and open parts of L-05 and L-12. The biometric slot's vault half (`BiometricKeySpecTest` and the slot-commit parts of L-30, L-33 and L-35, and `PasswordReminderTest` and `PasswordReminderPersistenceTest` of L-37) comes with the first `KeyVault` code that writes a biometric slot.
6. `DbMaintenance` round trips, restore validation, failure and crash injection, reconciliation, before any Backup, Restore or encryption setting is visible: L-06–L-11, L-14–L-16 and the mechanics of L-24, L-34 and L-36.
7. `SessionGate` and lock rules, before the gate screens: L-02, L-18, L-19, L-29, L-31, L-32, L-38, L-39, and the gate-state halves of L-01, L-05, L-12, L-24, L-33 and L-37.
8. UI: I-31–I-38, I-42 (e)–(g), I-44–I-46, I-50, L-20–L-26, and the Compose halves of I-21–I-23, L-03 (`PasswordScreenTest`), L-05, L-12, L-24, L-36 and L-37. I-39 and I-40 grow with every new class and flow. The `@RealBiometric` tests of L-30 and L-31 exist before the first release that offers the biometric lock in Password mode.
9. Performance and release checks from the first release build; performance sign-off before release ([section 8](#8-performance-tests)).

## 5. Security and lifecycle tests

Mechanics are defined in [security.md](security.md) and [db-lifecycle.md](db-lifecycle.md). Snapshots are taken with `DatabaseHolder` closed, so WAL files are checkpointed and removed, and use `fileFingerprint` (length, SHA-256, `lastModified`). Three comparisons are used, because opening the live file rewrites page 1 when SQLite switches the journal mode (db-lifecycle.md § Open sequence), so a main file is never byte-identical across an open:
- **Untouched** (no database connection was opened by the action): every `doro-*.db` main file and `db-state.json` has equal length, SHA-256 and `lastModified`, and the sets of file names in `databases/`, `noBackupFilesDir/staging/`, `noBackupFilesDir/restore/` and `cacheDir/share/` are equal.
- **Unchanged** (the live file may have been opened): `db-state.json` has equal length and SHA-256; the set of main file names is equal; `canonicalDump` of the live generation, opened with the same key, equals the dump taken before; `staging/`, `restore/` and `share/` hold nothing new; no new `doro-*` file exists.
- **Kept** (corrupt or unreadable files): every main file still exists and `db-state.json` is unchanged.
`-wal`, `-shm` and `-journal` files and `lastModified` of main files are never compared except under "Untouched".

Failure-injection techniques:
- **SQL rollback (I-19)**: the test adds a real trigger to its throwaway database, for example `CREATE TRIGGER t_fail BEFORE INSERT ON note_projects WHEN NEW.project_id = 7 BEGIN SELECT RAISE(ABORT, 'injected'); END`, or the same on `BEFORE UPDATE OF date ON notes` and `BEFORE DELETE ON notes` or `persons`. No production seam is needed.
- **Exceptions (L-14)**: `DbMaintenance` calls `MaintenanceFaultHook.before(op, step)` immediately before every `PipelineStep` of the db-lifecycle.md step table; `AppContainer.faultHook` defaults to a no-op in release. `ThrowingFaultHook(op, step, error)` and `BlockingFaultHook(op, step)` (suspends the operation on a latch until the test releases it) live in `src/sharedTest`; `op = null` addresses `completeStartup`.
- **Process death (L-15)**: a debug-only `CrashTestService` (`src/debug/AndroidManifest.xml`, `android:process=":crashtest"`, `android:exported="false"`). `DoroApplication.onCreate` returns right after `super.onCreate()` when `Application.getProcessName()` is not the package name, so `:crashtest` never starts the production container or the gate. The bind `Intent` carries `op` (a `MaintenanceOp` name, or `Startup` for `completeStartup`), `origin`, `step` (a `PipelineStep` name), passwords as `ByteArray` extras, a restore input planted at `noBackupFilesDir/crashtest-in/input.db`, and a backup target `Uri.fromFile(File(cacheDir, "crashtest-out/backup.db"))` (opened with `"wt"` like any document Uri). `onBind` returns a plain `Binder`; on a background thread the service builds `AppContainer(application)` with `faultHook = MaintenanceFaultHook { o, s -> if (o == op && s == step) Process.killProcess(Process.myPid()) }` (`KillingFaultHook`, `src/debug`), runs the SQLCipher init of security.md § 3.4 and runs the operation directly through `DbMaintenance`, without `SessionGate`. The test runs in the instrumentation process, where no container has started ([section 7](#7-fixtures-and-fakes), wiring). It prepares files and key state with a container it builds and closes itself, so nothing is open there (db-lifecycle.md § Concurrency rules, rule 9), binds with `BIND_AUTO_CREATE`, registers an `IBinder.DeathRecipient` through `linkToDeath` (a `RemoteException` counts as already dead) and waits for `binderDied()` with a 60 s wall-clock timeout; if the process is still alive the step was never reached and the test fails. It then builds a fresh container, starts the gate, waits for a terminal gate state and asserts the matrix row. A thrown exception is not a substitute, because `finally` blocks would run and hide leftovers. The recovery origin is not inferred: the service passes `MaintenanceOrigin` (`Corrupt` or `KeyUnavailable`) to `restore` and `startFresh` exactly as the screens do ([db-lifecycle.md § Operation frame](db-lifecycle.md#operation-frame), step 4).
- **Biometric slot (L-30–L-39, I-50)**: the GMD tests run the real `KeyVault` with the Keystore-operations seam of security.md § 3.6 in its test configuration, which generates the biometric key with the production alias, key size, GCM mode and purposes but without the user-authentication parameters, so a `Cipher` works without a touch. `FakeBiometricGateway` answers a prompt that carries a `CryptoObject` by returning that same object, so the slot's wrap and unwrap run real AES-GCM inside AndroidKeyStore. Invalidation is injected by the seam throwing `KeyPermanentlyInvalidatedException` from `Cipher.init` on the biometric key, or by deleting the biometric alias with `KeyStore.deleteEntry`. The test configuration is a constructor argument that only `src/androidTest` passes; the production `AppContainer` always uses the default, and `BiometricKeySpecTest` pins the production spec. What the seam skips (the authentication parameters, the binding of the cipher to a real touch, invalidation by a real enrollment change) is covered by the `@RealBiometric` tests and M-22–M-25 ([section 2.1](#21-biometric-slot-tests-what-runs-where)).
- **File damage**: `corruptPage`, truncation to half, a 0-byte file, flipped bytes in the key-state JSON; Keystore loss through `KeyStore.getInstance("AndroidKeyStore").deleteEntry(alias)` with the alias constant from security.md.
- **Runtime corruption (L-12)**: after the gate reaches Ready and before any list is collected, with Room open and the WAL empty, the test uses `RandomAccessFile` on the live main file to overwrite pages 2 to `PRAGMA page_count` with random bytes (Plain) or to flip one byte in each of those pages (Device). It then collects the All list, so the first read on a Room reader connection fails.
- **Recording document provider (L-08)**: `RecordingDocumentsProvider`, declared in `src/debug/AndroidManifest.xml` (authority `${applicationId}.testdocs`, `android:exported="false"`), runs in the app process, so the test reads its static record directly. It stores files in `cacheDir/recording-provider/`, records the mode of every `openFile` and, to mimic non-truncating providers, opens mode `"w"` with `MODE_WRITE_ONLY or MODE_CREATE` without `MODE_TRUNCATE`. ## 7. Fixtures and fakes

`FakeAppTime` implements the `AppTime` API from [architecture.md § Time](architecture.md#time), all five members. Time stands still until a test moves it, so ties are always deliberate:

```kotlin
class FakeAppTime(
    start: Instant = Instant.parse("2026-11-17T09:00:00Z"),
    zone: ZoneId = ZoneId.of("Europe/Berlin"),
) : AppTime {
    var instant: Instant = start; private set                       // wall clock
    var zone: ZoneId = zone; private set
    var elapsed: Long = 10_000_000L; private set                    // monotonic clock; moves back only through setElapsed (a simulated reboot)
    var tickPerNowCall: java.time.Duration = java.time.Duration.ZERO // see I-06
    private val today = MutableStateFlow(localDate())
    override fun nowMillis(): Long {
        val now = instant.toEpochMilli()
        if (!tickPerNowCall.isZero) { instant = instant.plus(tickPerNowCall); elapsed += tickPerNowCall.toMillis() }
        return now
    }
    override fun today(): LocalDate = localDate()
    override fun dateOf(epochMillis: Long): LocalDate = Instant.ofEpochMilli(epochMillis).atZone(zone).toLocalDate()
    override fun elapsedMillis(): Long = elapsed
    override val todayFlow: StateFlow<LocalDate> = today
    fun advanceBy(d: java.time.Duration) { require(!d.isNegative); instant = instant.plus(d); elapsed += d.toMillis(); today.value = localDate() }
    fun setWallClock(i: Instant) { instant = i; today.value = localDate() }   // the user changed the clock; elapsed does not move
    fun setElapsed(ms: Long) { elapsed = ms }                       // settable monotonic clock: lock exemption, backoff, KDF timing; a smaller value simulates a reboot
    fun setZone(z: ZoneId) { zone = z; today.value = localDate() }
    private fun localDate(): LocalDate = instant.atZone(zone).toLocalDate()   // not LocalDate.ofInstant (API 34); this runs on api28
}
```

Each timer names its clock. The DEC-62 `unlock_retry_at` and `NeedsPassword.retryAt` use `elapsedMillis()` ([security.md § 5.3](security.md)), and so does the 10-minute lock exemption (security.md § 7.7); the share sweep compares `nowMillis()` with `File.lastModified()`, and the one-hour share timer is a coroutine delay on the test scheduler. Tests that plant share files set `lastModified` relative to `FakeAppTime.nowMillis()`, never relative to the device clock. `advanceBy` moves both clocks; `setWallClock` moves only the wall clock (a `TIME_SET` or a clock set back); `setElapsed` sets only the monotonic clock.

A test that plants files, key state or DataStore values sets `autoStart = false`, plants through `rule.container` or `DbFiles`, and then calls `rule.start()`. `after()` cancels the test `applicationScope` and closes the holder. Tests that do not launch `MainActivity` (DAO, repository, `KeyVault`, `DbMaintenance`, reconciliation) construct their objects directly and never touch `app.container`. The `startApp()` hook, the process guard and the container members `biometricGateway`, `processLifecycle` and `faultHook` are defined in [architecture.md § Dependency injection](architecture.md#dependency-injection).

Debug-only QA hook `DebugWallClockOffset` (`src/debug`, used by M-24): the debug `AppContainer` builds `DefaultAppTime` with `instant = { Instant.now().plusMillis(offsetMs) }`, where `offsetMs` is read from the file `files/debug-wall-offset-ms` (a decimal `Long`, may be negative) at process start and at every process ON_START; a missing or unparsable file means 0. It moves only the wall clock (`nowMillis()`, `today()`), never `elapsedMillis()`, so the backoff and the lock exemption are unaffected. The tester sets it with `adb shell run-as com.doro.organizer sh -c 'echo 1209660000 > files/debug-wall-offset-ms'` and removes it with `adb shell run-as com.doro.organizer rm files/debug-wall-offset-ms`. Notes edited while an offset is set carry shifted timestamps, so M-24 runs on a scratch dataset. Release, `qa` and `benchmark` builds have no such file and pass `Instant::now` ([architecture.md § Per-build-type files](architecture.md#per-build-type-files) owns the per-build-type wiring); the `release-logs` and `manifest` jobs need no change because the hook is neither a component nor a log call. The file holds no user data.

`SENTINEL = "Zq7SentinelXk"` (in `src/sharedTest`) is the marker that I-39, I-40, L-03, L-21 and M-17 search for; no other doc defines a sentinel.

## 8. Performance tests

Budgets, and the statistic each one is asserted on, live in [architecture.md § Performance budgets](architecture.md#performance-budgets); this section defines how they are measured. Tests are annotated `@PerfTest`, excluded from PR runs, and run nightly on `api28` and `api35` against the 10,000-note seed with the `benchmark` build type of [section 9](#9-ci-pipeline), because debuggable builds are not comparable to a release build. Debug builds are never measured. Each measurement makes 3 warm-up runs and 10 measured runs, reads `SystemClock.elapsedRealtimeNanos()`, records the median, the p90 (9th of the 10 sorted values) and the maximum as JSON in the instrumentation's `additionalTestOutputDir` (Verify at setup: GMD pulls that directory). On a GMD emulator a P-n fails when its budget statistic (p90 for the list-query budget, median for the others) exceeds 2 × the architecture.md value. On Physical B the exact budget applies (release sign-off, M-18).

| ID | Measurement | Budget |
|---|---|---|
| P-1 | Perspective query to first Flow emission: All; the 2,000-note person; the 1,500-note project; a busy day; a one-year range; Orphan; search for a common three-letter term and for a miss. Also recorded: calendar month marks, Select all ids, delete-impact counts for the 2,000-note person | First emission ≤ 100 ms p90 for the first group; the rest recorded only |
| P-2 | Perspective switch (Compose): from `performClick()` on a tab to the first frame in which the target list's first row is displayed (`waitUntil` on that row node), inside trace section `doro:switch` | ≤ 250 ms |
| P-3 | Write to re-emission: checking a note in All until the list re-emits (whole-list query, DEC-10) | Recorded only; fails only if architecture.md sets a budget |
| P-4 | Maintenance on the seed: backup export, restore, Plain → Device key change | Recorded only; fails only if architecture.md sets a budget |
| P-5 | Cold start of the release-like build on Physical B with `seed-10k` restored through Settings → Restore: `adb shell am start -S -W -n <applicationId>/com.doro.organizer.MainActivity`, 1 warm-up plus 10 runs, recording `TotalTime` and the "Fully drawn" time that `ReportDrawnWhen { !uiState.loading }` logs (read from `adb logcat -d`, tag `ActivityManager` on API 28 and `ActivityTaskManager` on API 29+), lock off. Password mode (to the password screen, `TotalTime`) is recorded without a budget | Median Fully drawn ≤ 1,500 ms in Plain, ≤ 1,700 ms in Device mode |
| P-6 | Editor open (Compose): from `performClick()` on a row to the editor text field holding the note's content (`waitUntil` on a node with the first 20 characters), for a 2,000-character note and for one of the seed's 200,000-character notes, inside trace section `doro:editor` | ≤ 300 ms and ≤ 600 ms |
| P-7 | Batch on 1,000 seed notes: `NoteRepository.associate` (2 persons and 1 project), `setDate` and `deleteNotes`, wall time of each suspend call, one transaction each | ≤ 1,000 ms each |

Macrobenchmark is optional and currently excluded: it needs a separate `com.android.test` module, which DEC-03 (single `:app` module) does not allow. P-5 uses `am start -W` until DEC-03 changes.

Choose the fingerprint reset: one touch, then a new password twice with the acknowledgement: the app opens with the same number of notes, followed by one prompt to set fingerprint unlock up again (accept it). Force-stop, start, "Use password": the old password is refused and the new one opens. Type five wrong passwords so the screen is throttled, then run the reset again: it works during the countdown. Turn the biometric lock off: "Forgot password?" now offers only "Erase all data and start over" (do not confirm it unless a backup was made).
