# Testing

This document defines how Doro Organizer is verified: test layers, devices, the order in which suites must exist, the invariant catalog, security and lifecycle tests, §13 traceability, fixtures and fakes, performance measurement, CI gates and the manual release checklist.

Related: [decisions.md](decisions.md) · [architecture.md](architecture.md) · [data-layer.md](data-layer.md) · [ui.md](ui.md) · [security.md](security.md) · [db-lifecycle.md](db-lifecycle.md) · [spec](../stakeholder-notepad-spec.md)

Conventions: catalog ids are `I-nn` (invariants and behavior), `L-nn` (security and lifecycle), `P-n` (performance) and `M-nn` (manual). Catalog ids always carry two digits (`I-05`). data-layer.md numbers its invariants `INV-1` to `INV-12` and its restore checks `R-1` to `R-5` ([data-layer.md](data-layer.md) § Invariants), so a bare `I-nn` here is always a catalog id. Other docs cite catalog ids with the prefix "testing.md". "Instr" means instrumented. The mapping from data-layer.md's invariants to catalog rows is at the end of [section 4](#4-invariant-catalog).

## 1. Test layers

Build and test from the command line only (DEC-15): the Gradle wrapper and `adb`. No Android Studio and no emulator are required. Every instrumented and Compose test runs on the owner's Poco F7 (Physical A, [section 2](#2-device-matrix)), connected over USB, with `./gradlew :app:connectedDebugAndroidTest`. The debug build has `applicationIdSuffix = ".debug"` (applicationId `com.doro.organizer.debug`), so tests that clear the app's data and Keystore entries never touch the owner's notes in the release app (`com.doro.organizer`); the `qa` and `benchmark` builds carry their own suffixes for the same reason (sketch in [section 9](#9-ci-pipeline)). Gradle Managed Devices (GMD) and emulator jobs are optional extras, never required gates. Code that exists only on API 28–29 (the device-credential intent, the biometric key's validity −1, `fullBackupContent`, the missing Recents screenshot API) is never run on a device: lint `NewApi`, JVM tests of the branching logic and review cover it, and that gap is an accepted risk (DEC-15). In the table below, "device" means the connected phone.

Rules for every test:
- Anything that touches SQLCipher is instrumented (DEC-12): its `.so` files cannot load on the JVM or under Robolectric. No DAO, query or migration test may run on the framework SQLite instead, because its `LIKE` is ICU-enabled and its error handler deletes files (DEC-08). Robolectric is not used.
- No mocking library (DEC-12). Fakes are hand-written. Code that never calls Android at runtime (`FakeAppTime`, `FakeKeyVault`, `FakeSettingsStore`, `FakeBiometricGateway` and the process `LifecycleOwner` `TestProcessLifecycle`, whose Android types appear only in signatures and which the JVM controller tests need, `LockFixture`, `SENTINEL`, the pure `SeedModel` generator, the oracle comparator) lives in `app/src/sharedTest/java/com/doro/organizer/testing/`, a directory that `app/build.gradle.kts` adds to the `test` source set and to `androidTest` for `debug` and `benchmark` ([section 9](#9-ci-pipeline) sketch). A test class that must run on both layers lives there too, in its production package: `src/sharedTest/java/com/doro/organizer/security/Pbkdf2KatTest` (L-27, JVM + Instr). Everything that needs a `Context`, SQLCipher or androidx.test (`DoroTestRunner`, `TestDoroApplication`, `DoroAppRule`, `TestDatabases`, the seed database writer, `corruptPage`, `fileFingerprint`, `canonicalDump`, the annotations `PerfTest`, `PageSizeSmoke` and `RealBiometric`) lives in `app/src/androidTest/java/com/doro/organizer/testing/`, so a JVM test can never compile against SQLCipher helpers. `ReleaseSmoke` lives in `app/src/androidTestQa/java/com/doro/organizer/testing/` with `ReleaseSmokeTest` (DEC-103 (5)). The `benchmark` test APK compiles only the `perf` and `testing` packages of `src/androidTest` plus `src/sharedTest` and `src/androidTestRelease`, so a perf test and every fixture it uses must live there. Verify at setup: AGP's `testFixtures` is not used because it targets library modules; if AGP 9.5 supports it for an application module it may replace `src/sharedTest`.
- No fake exists for `NoteRepository`, `EntityRepository`, `DatabaseHolder` or `DbMaintenance`, so no fake can drift from the SQL or the file protocol. Stand-ins built on `unused<T>()` that script a few answers of `NoteRepository`, `DbMaintenance` or `AppLockController` for the rules of one ViewModel or screen (`ListFakes`, `EditorFakes`, `ForgotPasswordViewModelTest`, `SettingsViewModelTest`, and the scripted gate fixtures of section 7, among them `ScriptedDataCheck`, which wraps the real repository and answers only `hasAnyData()`) are not such fakes: each scripts results whose producing code is tested against the real component. The fakes are `FakeAppTime`, `FakeSettingsStore`, `FakeKeyVault`, `FakeBiometricGateway` and the hand-written process `LifecycleOwner` ([section 7](#7-fixtures-and-fakes)).
- JVM tests call no Android API at runtime (the stubs in `android.jar` throw). A class that needs a `Context`, a `Uri` or `android.icu` is tested instrumented. ViewModels are tested instrumented on the real repositories. JVM tests construct the `SessionGate` reducer and the pure policies directly, and run the real `DefaultAppLockController` and `DefaultSessionGate` over the fakes (`LockFixture`, `GateLockWiringTest`; section 7), which make no Android call at runtime with them. A test that reaches `confirmWithPassword` (NFC through `android.icu`) or `AppLog` (`android.util.Log`) is instrumented, because `unitTests.isReturnDefaultValues` is off.
- Instrumented tests are hermetic (from T3, when `DoroTestRunner`, the Orchestrator and `clearPackageData` are added; the T1 skeleton runs the plain `AndroidJUnitRunner`, [section 9](#9-ci-pipeline)). Android Test Orchestrator with `clearPackageData=true` runs `pm clear` on the app under test after each test, which deletes its files, DataStore and Keystore entries. That is safe on the owner's phone because the app under test is the debug build `com.doro.organizer.debug`, whose data is separate from the release app's (DEC-15); `connectedDebugAndroidTest` installs and removes only that app and its test APK. Before the suite the runner script executes `adb shell pm clear <applicationId>` with the debug id. No script or test ever runs `pm clear` or `adb uninstall` for `com.doro.organizer`, the owner's real app. GMD runs, if used, start from a fresh install. No test depends on the order or leftovers of another.
- Tests and scripts never change the phone's system state: no `locksettings`, no fingerprint enrollment, no clock or developer-setting changes on Physical A. The one `locksettings` technique (L-19, `PromptInfoTest`) is emulator-only and guarded by `assumeTrue`, so it is skipped on the phone. Time in tests is `FakeAppTime`; only the manual item M-24 moves a clock, and says how to restore it.
- Behavior under test reads time only from `FakeAppTime` ([section 7](#7-fixtures-and-fakes)). To wait, use Turbine (`flow.test(timeout = 10.seconds) { }`; Turbine timeouts run on the wall clock) or `composeTestRule.waitUntil(timeoutMillis = 10_000) { }`. Give every `runTest` an explicit `timeout` (`runTest(timeout = 120.seconds)` when the 10,000-note seed is used). Never wrap work that runs on Room executors or `dispatchers.io` in `withTimeout` or `delay` inside `runTest`: virtual time would jump to the timeout at once. No `Thread.sleep`. `@PerfTest` measurements read `SystemClock.elapsedRealtimeNanos()` ([section 8](#8-performance-tests)). Dispatchers are injected as [architecture.md § Threading](architecture.md#threading) defines.
- Spec strings and ui.md strings are asserted as literals copied from the spec or from [ui.md § 11 Strings](ui.md#11-strings), never through `R.string`, so an edited resource fails a test (DEC-55). Nodes are found by the tags of [ui.md § 12.8](ui.md#128-test-tags).
- Never launch or recreate `MainActivity` while the gate is `Starting`. `MainActivity` keeps its splash screen while the gate is `Starting`, so the activity draws no first frame and `ActivityScenario` waits for it with no timeout (`startActivitySync` on a launch, `waitForIdleSync` on a recreate); a scripted gate never leaves `Starting` by itself, so the whole run hangs. The scenes refuse both steps at once (`checkNotStarting`, `checkRecreatable`, [section 7](#7-fixtures-and-fakes)): a test launches in a later state and moves the gate to `Starting` with the activity up, awaits a real gate past `Starting` first, or recreates there with `ScriptedGateScene.recreateWhileStarting()` (I-52 (a)). Only `GateScene.coldStart()` launches in `Starting`, unguarded, because the real gate leaves it by itself; a test that holds startup back (a `faultHook` target on the way to the first state) must not cold-start, or the launch never returns.
- Before tapping a node in a scrolling container, a Compose test scrolls it into view and asserts that it is displayed (`GateUi.click`, or `performScrollTo().assertIsDisplayed()`): `performClick` taps the centre of the node's clipped bounds, so the tap on a node wholly outside the visible part is lost without an error. `assertTouchTarget` is no visibility check: it measures touch bounds (Q13), not what is shown.
- While the soft keyboard is shown, the first Back only hides it ([ui.md § 2.5](ui.md#25-back-behavior)), so a Back meant for the app follows `closeKeyboard` (`Keyboard.kt`, [section 7](#7-fixtures-and-fakes)).
- When `Intents.init()` runs before the activity launch, Espresso-Intents also records the scenario's own `MAIN`/`LAUNCHER` start of `MainActivity` and the `InstrumentationActivityInvoker` activities that `moveToState` and `close` start, so a test counts or reads the app's intents only through `appIntents()`.
- Under a Compose rule, a test waits for anything a composable effect starts with a wait that advances the Compose clock (`compose.waitUntil`); for prompts that is `GateComposeTest.awaitPrompts`, the only prompt wait. A plain coroutine wait such as `GateScene.awaitGate` does not advance the Compose clock, so it suits only what the gate or a ViewModel starts by itself, and a blocking wait on the test thread never sees a prompt that the test's own coroutine starts.
- A node under `clearAndSetSemantics` (an editor link chip, a filter chip, the parts of a note row) keeps no `Text` in the merged tree, so a test finds it by its content description (`GateUi.awaitDescription`). A non-clickable M3 `Card` or `Surface` does not merge its children, so its text is asserted through `hasAnyDescendant`.
- A locale-formatted date (rows, chips, the editor and the picker meta) is expected in the phone's configuration locale and built with `java.time` (`DateTimeFormatter.ofLocalizedDate(FormatStyle.MEDIUM)`), not with the app's own formatter; only `DateDisplayTest` (I-31) pins per-locale literals.
- Four owner questions are open, Q13 to Q16 ([decisions.md § Owner questions](decisions.md#owner-questions)). Every test that pins the default of an open question ends its method name with the question id: `TouchTargetSweepTest.aVisibleClickableLaidOutSmallerThan48dp_passes_onItsPaddedTouchBounds_Q13` pins Q13; Q14 has no pinning test, because its default is a known crash; `NotePreviewTest.preview_isStoredFromTheBoundContent_onInsertAndUpdate_Q15` and `NoteRowMappingTest.linkIds_resolveThroughTheNameMaps_andARowWaitsForAMissingName_Q15` pin Q15; Q16 has no pinning test, because its default is the library's own behavior (`AtomicFile` only logs a failed sync, DEC-107 (4)) and the phone cannot make a sync fail. Only pinning methods carry the suffix, never a wildcard over a class, and answering the question starts with a search for `_Qn`. Answered questions are cited in the catalog text like decisions (for example "(Q7)"), never in test names. No test named with `_Q8` or `_Q11` exists any more (both questions are answered, DEC-65 and DEC-71); the `test-names` job of [section 9](#9-ci-pipeline) fails on any test method whose name ends in the id of an answered question (the rows of the "Answered" table of decisions.md), so the pinning tests of open questions pass.
- Tests never hard-code an applicationId (DEC-03, DEC-15): instrumented tests run as the debug build `com.doro.organizer.debug` and use `targetContext.packageName`; scripts take the id from the build (the gate tasks read each variant's `applicationId` from AGP's variant API, [section 9](#9-ci-pipeline); a shell script that needs it may use `apkanalyzer manifest application-id`). Only the `manifest` job compares ids with literals: the release id with `com.doro.organizer`, the debug, `qa` and `benchmark` ids with that value plus `.debug`, `.qa` and `.benchmark`.
- Instrumented-test code that reaches the debug-only hooks (package `com.doro.organizer.debug`: `testBioKeySpec`, `RecordingDocumentsProvider`, the crash seams; and the debug `DebugTools.fontScale`) lives in `src/androidTestDebug/java`, so the `qa` and `benchmark` test APKs compile without those hooks; `src/androidTestRelease/java` holds the counterparts the `benchmark` test APK compiles instead (the `qa` test APK compiles only `src/androidTestQa`, DEC-103 (5)) (`testBioKeystore()`: the production key spec there). Everything else stays in `src/androidTest`, except `BiometricSlotDeviceTest`, which lives in `src/androidTestDebug/java` (the `real-biometric` job runs it against the debug app only), and `ReleaseSmokeTest` and `@ReleaseSmoke`, which live in `src/androidTestQa/java`, the only sources of the `qa` test APK (DEC-103).
- Every bug fix lands with a test that fails without the fix.
- Every instrumented `@Test` function returns `Unit`: with an expression body, write `= runBlocking<Unit> { … }` or `= runTest { … }`. A `runBlocking { … }` whose last expression has a value makes the method non-void; JUnit then rejects the whole class with `initializationError`, AGP's result XML leaves the class out, and `connectedDebugAndroidTest` still exits 0. Four classes (`ExternalActivitiesTest`, `session.CorruptionTest`, `session.SlotOpenRejectTest`, `StartupEventTest`, 10 tests) never ran until the T22 device run noticed it. Two guards (T24): `ArchitectureTest.instrumentedTestMethods_areAllAcceptedByJUnit` (JVM, before any device run; its planted twin compiles a Java class with `javax.tools` at test time) reads the compiled instrumented test classes, not the sources, because a source rule cannot see the return type of `runBlocking { … }` or of a helper wrapper. `app/build.gradle.kts` makes every unit-test task depend on `compile<TestBuildType>AndroidTestKotlin` and passes that task's `destinationDirectory` (`src/sharedTest` included) as the system property `doro.androidTestClasses` through a `@Classpath` argument provider; `ClassFile` is a minimal class-file reader (superclass, fields, methods, runtime-visible annotations). `TestMethodRule` applies JUnit 4's validation to every class with a `@Test` method and its superclasses: `@Test`, `@Before` and `@After` methods public, not static, without parameters, returning `Unit`; `@BeforeClass` and `@AfterClass` the same but static; `@Rule` members public and not static (unless also `@ClassRule`), `@ClassRule` members public and static (a Kotlin `@Rule val` annotates the private field: write `@get:Rule`). It does not check a rule member's type or the class constructor. With `-PtestBuildType=qa` or `benchmark` that output holds only the narrowed sources of DEC-103 (5), so `TestMethodRule` sees fewer classes; the documented unit-test runs use `debug`. After every connected run, `:app:checkDeviceTestResults` (the `device-tests` job of [section 9](#9-ci-pipeline)) fails on a rejected class that slipped through.
- Test library versions are pinned in `gradle/libs.versions.toml` with the rest of the stack ([architecture.md § Stack and versions](architecture.md#stack-and-versions)). Verify at setup: current stable Turbine, AndroidX Test (runner, rules, ext-junit, orchestrator, espresso-intents, uiautomator) and Compose UI test through the BOM.

### 2.1 Biometric slot tests: what runs where

The Q8 unlock (DEC-60, DEC-65) cannot be tested end to end with a fake. A `BiometricPrompt` that carries a `CryptoObject` only authorizes the cipher after a real touch on a real sensor, the biometric key ([security.md § 3](security.md#3-key-model-dec-60), which owns its parameters) can only be generated while a strong biometric is enrolled, and its invalidation is triggered by a real enrollment change in system Settings. The suites are therefore split:

| What | Tests | Runs on | Why there |
|---|---|---|---|
| The production `KeyGenParameterSpec` of the biometric key, inspected without generating a key (API 30+ branch) | `BiometricKeySpecTest` (L-30) | Physical A, every PR | Building a spec needs no enrolled biometric |
| The API 28–29 branch of the key parameters (validity −1) | `BiometricKeySpecTest`, pure-function half (L-30) | Local JVM, every PR | No API 28–29 device runs (DEC-15). The test needs the choice of authentication parameters to be a pure function of `sdkInt` that `bioKeySpec` calls: `bioKeyAuth(sdkInt)` ([security.md § 3.7.1](security.md) defines both) |
| Slot creation, unwrap, deletion and re-creation logic, the lock toggles, the gate paths, "Use password", the reminder, the fingerprint reset, the KeyUnavailable lock route, the kekBroken notice, the KEK fallbacks of DEC-86 (gate and restore key), the key-store line and its ON_START re-check, the clearing of the kekBroken notice and flag, the Forgot password ViewModel state, the Q7 limit, the strings and screens | L-30–L-54, I-50–I-55, all except the device classes below | Physical A, every PR | Runs the real `KeyVault` with the test configuration of the Keystore-operations seam and `FakeBiometricGateway` ([section 5](#5-security-and-lifecycle-tests), technique "Biometric slot") |

## 5. Security and lifecycle tests

Mechanics are defined in [security.md](security.md) and [db-lifecycle.md](db-lifecycle.md). Snapshots are taken with `DatabaseHolder` closed, so WAL files are checkpointed and removed, and use `fileFingerprint` (length, SHA-256, `lastModified`). Three comparisons are used, because opening the live file rewrites page 1 when SQLite switches the journal mode (db-lifecycle.md § Open sequence), so a main file is never byte-identical across an open:
- **Untouched** (no database connection was opened by the action): every `doro-*.db` main file and `db-state.json` has equal length, SHA-256 and `lastModified`, and the sets of file names in `databases/`, `noBackupFilesDir/staging/`, `noBackupFilesDir/restore/` and `cacheDir/share/` are equal.
- **Unchanged** (the live file may have been opened): `db-state.json` has equal length and SHA-256; the set of main file names is equal; `canonicalDump` of the live generation, opened with the same key, equals the dump taken before; `staging/`, `restore/` and `share/` hold nothing new; no new `doro-*` file exists.
- **Kept** (corrupt or unreadable files): every main file still exists and `db-state.json` is unchanged.
`-wal`, `-shm` and `-journal` files and `lastModified` of main files are never compared except under "Untouched".

## 7. Fixtures and fakes

`FakeAppTime` implements the `AppTime` API from [architecture.md § Time](architecture.md#time), all five members. Time stands still until a test moves it, so ties are always deliberate:

```kotlin
class FakeAppTime(
    start: Instant = Instant.parse("2026-11-17T09:00:00Z"),
    zone: ZoneId = ZoneId.of("Europe/Berlin"),
) : AppTime {
    var instant: Instant = start; private set                       // wall clock
    var zone: ZoneId = zone; private set
    var elapsed: Long = 10_000_000L; private set                    // monotonic clock; moves back only through setElapsed (a simulated reboot)
    var tickPerNowCall: java.time.Duration = java.time.Duration.ZERO // see I-06
    private val today = MutableStateFlow(localDate())
    override fun nowMillis(): Long {
        val now = instant.toEpochMilli()
        if (!tickPerNowCall.isZero) { instant = instant.plus(tickPerNowCall); elapsed += tickPerNowCall.toMillis() }
        return now
    }
    override fun today(): LocalDate = localDate()
    override fun dateOf(epochMillis: Long): LocalDate = Instant.ofEpochMilli(epochMillis).atZone(zone).toLocalDate()
    override fun elapsedMillis(): Long = elapsed
    override val todayFlow: StateFlow<LocalDate> = today
    fun advanceBy(d: java.time.Duration) { require(!d.isNegative); instant = instant.plus(d); elapsed += d.toMillis(); today.value = localDate() }
    fun setWallClock(i: Instant) { instant = i; today.value = localDate() }   // the user changed the clock; elapsed does not move
    fun setElapsed(ms: Long) { elapsed = ms }                       // settable monotonic clock: lock exemption, backoff, KDF timing; a smaller value simulates a reboot
    fun setZone(z: ZoneId) { zone = z; today.value = localDate() }
    private fun localDate(): LocalDate = instant.atZone(zone).toLocalDate()   // not LocalDate.ofInstant (API 34): minSdk is 28 and lint NewApi flags it
}
```

Each timer names its clock. The DEC-62 `unlock_retry_at` and `NeedsPassword.retryAt` use `elapsedMillis()` ([security.md § 5.3](security.md)), and so does the 10-minute lock exemption (security.md § 7.7); the share sweep compares `nowMillis()` with `File.lastModified()`, and the one-hour share timer is a coroutine delay on the test scheduler. Tests that plant share files set `lastModified` relative to `FakeAppTime.nowMillis()`, never relative to the device clock. `advanceBy` moves both clocks; `setWallClock` moves only the wall clock (a `TIME_SET` or a clock set back); `setElapsed` sets only the monotonic clock.

The production `AppTime` is `DefaultAppTime(instant: () -> Instant, zone: () -> ZoneId, scope: CoroutineScope)` with the entry points `onStart()`, `onStop()`, `onResume()` and `onTimeChanged()`, which the Android glue in `core.time` (the `ProcessLifecycleOwner` observer and `TimeChangeReceiver`) calls, so `AppTimeTest` drives midnight, DST and zone changes in virtual time (I-30). The constructor and the entry points are defined in [architecture.md § Time](architecture.md#time).

## 8. Performance tests

Budgets, and the statistic each one is asserted on, live in [architecture.md § Performance budgets](architecture.md#performance-budgets); this section defines how they are measured. Tests are annotated `@PerfTest`, excluded from PR runs, and run on demand and before release on the sign-off phone (Physical B when available, otherwise Physical A) with `./gradlew :app:connectedBenchmarkAndroidTest -PtestBuildType=benchmark` against the 10,000-note seed and the `benchmark` build type of [section 9](#9-ci-pipeline) (application id `com.doro.organizer.benchmark`), because debuggable builds are not comparable to a release build. An optional nightly run on GMD emulators uses the same tests. Debug builds are never measured. Each measurement makes 3 warm-up runs and 10 measured runs, reads `SystemClock.elapsedRealtimeNanos()`, records the median, the p90 (9th of the 10 sorted values) and the maximum as JSON through `androidx.test.services` TestStorage (`/sdcard/googletest/test_outputfiles`, owned by the test services app, which the Orchestrator's `clearPackageData` of the app under test does not touch). With `-PtestBuildType=benchmark`, `app/build.gradle.kts` passes the instrumentation argument `useTestStorageService=true`, and AGP then copies that directory into `app/build/outputs/connected_android_test_additional_output/benchmarkAndroidTest/connected/<device>/` after the run. Verified at setup (SPEC T22, 2026-11-22, Poco F7): the instrumentation's `additionalTestOutputDir` lies in the app's data, which `clearPackageData` deletes after every test, so only the last test's file reached the host; through TestStorage all six JSON files and `seed-10k.db` arrived. Verify at setup (GMD): that the TestStorage output of the optional `api28` and `api35` runs reaches the additional test output (only the connected phone run was checked; storage permissions differ on API 28). On an optional GMD emulator a P-n fails when its budget statistic (p90 for the list-query budget, median for the others) exceeds 2 × the architecture.md value. On the sign-off phone the exact budget applies (release sign-off, M-18). Without Physical B the sign-off runs on Physical A, which is a fast phone, so a pass there is weaker evidence than a pass on the low-end reference device (accepted, DEC-15).

## 9. CI pipeline

There is no hosted-CI requirement (DEC-15): every job is a command-line step (Gradle wrapper, `adb`, `git`, `sh`, and the SDK build-tools `zipalign` and `dexdump`, which the gate tasks call themselves) that runs on the developer machine or on any runner the owner attaches the phone to. Jobs marked optional never gate a merge or a release. `apkanalyzer`, `aapt2` and `readelf` are not used by any gate: `apkanalyzer` is a `.bat` on Windows, path-shortened resources cannot be read back from the APK, and `readelf` is not installed on the build machine (no NDK, and Git Bash ships no binutils) (DEC-14).

**Gate commands (DEC-14).** The `manifest`, `page-size` (static part), `release-logs` and `dependencies` jobs are Gradle tasks of the build-only included build `build-logic` (DEC-03; layout in [architecture.md § Build logic and gate configuration](architecture.md#build-logic-and-gate-configuration-dec-03-dec-14)), and the `schema` job is a shell script:

```
./gradlew :app:verificationGates            # manifest, page-size, release-logs, dependencies, plus :build-logic:test
./gradlew :app:checkReleaseManifestPolicy   # manifest alone
./gradlew :app:checkReleasePageSize         # page-size (static part) alone
./gradlew :app:checkReleaseLogs             # release-logs alone
./gradlew :app:checkBannedDependencies      # dependencies alone
sh config/check-schemas.sh                  # schema (runs sh config/check-released-schemas.sh at its end)
./gradlew :app:checkDeviceTestResults       # device-tests result check of the last connected run (runs by itself after every connected run)
```

- `:app:verificationGates` builds the minified release APK itself (the three release gates consume AGP's `APK`, `MERGED_MANIFEST` and `OBFUSCATION_MAPPING_FILE` artifacts), so no separate `assembleRelease` step is needed. It also depends on `:build-logic:test`: the JVM unit tests that pin the gate rules (`ManifestRulesTest`, `FilePathsTest`, `PageSizeRulesTest`, `ElfLoadSegmentsTest`, `DexLogScannerTest`, `R8OutputsTest`, `BannedDependenciesTest`, `ConfigEntriesTest`, `ReleasedSchemasScriptTest`, `DeviceTestResultsTest`) run with the gates, because a gate is only as strong as its rules. `ReleasedSchemasScriptTest` runs `config/check-released-schemas.sh` in a throwaway git repository with a hermetic git configuration and needs `git` and `sh` on the path (on Windows `sh` is taken from the Git installation); a missing tool fails the test, it is never skipped.
- The manifest gate is named `checkReleaseManifestPolicy` because `checkReleaseManifest` is an existing AGP task.
- Every gate lists all of its violations in one failure ("Verification gate '<name>' failed (testing.md § 9)"), and none of them is cacheable.
- The scripts are always called through `sh` in this document and in `check-schemas.sh`, so they work without the executable bit and under Git Bash on Windows. The git index still records the bit: whoever commits them runs `git add --chmod=+x config/check-schemas.sh config/check-released-schemas.sh`, so that `./config/check-schemas.sh` also works on a POSIX checkout. Both scripts run from the repository root.

`config/check-released-schemas.sh` (abridged: the committed file adds comments):

```sh
set -u
list=config/released-schema-versions.txt
dir=app/schemas/com.doro.organizer.data.db.AppDatabase
failed=0

# Append-only (M-20): every version ever added to the list in a commit must still be listed.
listed=$(tr -d ' \t\r' < "$list")
for v in $(git log -p --no-textconv --format= -- "$list" | sed -n 's/^+[[:space:]]*\([0-9][0-9]*\)[[:space:]]*$/\1/p' | sort -u); do
  if ! printf '%s\n' "$listed" | grep -qx "$v"; then echo "released version removed from $list: $v"; failed=1; fi
done

while IFS= read -r line || [ -n "$line" ]; do
  v=$(printf '%s' "$line" | tr -d ' \t\r')
  case "$v" in '' | '#'*) continue ;; esac
  case "$v" in *[!0-9]*) echo "not a schema version in $list: $v"; failed=1; continue ;; esac
  f="$dir/$v.json"
  # The commit that added the version to the list; a version listed but not committed yet compares with HEAD.
  release=$(git log --reverse --format=%H -G "^[[:space:]]*$v[[:space:]]*\$" -- "$list" | head -n 1)
  base=${release:-HEAD}
  if ! git cat-file -e "$base:$f" 2>/dev/null; then
    echo "released schema not committed: $f"; failed=1
  elif ! git diff --quiet "$base" HEAD -- "$f" || ! git diff --quiet "$base" -- "$f"; then
    echo "released schema changed: $f"; failed=1
  fi
done < "$list"

exit "$failed"
```
